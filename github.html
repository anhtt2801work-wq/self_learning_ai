Hướng dẫn Git và GitHub

Mọi dự án AI nghiêm túc đều cần quản lý phiên bản: code thí nghiệm thay đổi liên tục, bạn cần quay lại bản chạy tốt, làm việc nhóm và chia sẻ kết quả. Trang này đưa bạn từ con số 0 đến quy trình làm việc thực tế trên GitHub.

Git và GitHub khác nhau thế nào?

  • Git là phần mềm quản lý phiên bản phân tán chạy trên máy bạn. Nó lưu lịch sử thay đổi của thư mục dự án dưới dạng các commit.
  • GitHub là dịch vụ web lưu trữ kho Git (repository) từ xa, thêm các tính năng cộng tác: issue, pull request, review, Actions (CI/CD), Pages... GitLab và Bitbucket là các dịch vụ tương tự.

Khái niệm cốt lõi cần nhớ:

Thuật ngữÝ nghĩa
Repository (repo)Thư mục dự án cùng toàn bộ lịch sử (thư mục ẩn .git).
CommitMột “ảnh chụp” trạng thái dự án kèm thông điệp, tác giả, thời gian và con trỏ tới commit cha.
Branch (nhánh)Con trỏ có tên trỏ vào một commit; commit mới sẽ đẩy con trỏ đi tiếp.

Cài đặt và cấu hình lần đầu

Cài Git từ git-scm.com/downloads (hoặc qua trình quản lý gói như apt, brew, winget), rồi khai báo danh tính. Thông tin này được ghi vào mọi commit của bạn.

git --version
git config --global user.name "Ten Cua Ban"
git config --global user.email "ban@example.com"
git config --global init.defaultBranch main
git config --global --list
MẹoDùng cùng địa chỉ email mà bạn đã thêm vào tài khoản GitHub để commit được gắn đúng với hồ sơ của bạn.

Xác thực với GitHub

Khi đẩy code lên GitHub bạn cần chứng minh danh tính. Hai cách phổ biến: SSH key hoặc HTTPS với token (GitHub không còn chấp nhận mật khẩu tài khoản cho thao tác Git qua HTTPS). Cách SSH gọn nhất về lâu dài:

# 1) Tạo khóa (giữ nguyên đường dẫn mặc định, nên đặt passphrase)
ssh-keygen -t ed25519 -C "ban@example.com"

# 2) In khóa công khai rồi dán vào GitHub:
#    Settings → SSH and GPG keys → New SSH key
cat ~/.ssh/id_ed25519.pub

# 3) Kiểm tra kết nối
ssh -T git@github.com
Không bao giờ chia sẻ khóa riêngChỉ file .pub được dán lên GitHub. File không có đuôi (id_ed25519) là khóa riêng tư, tuyệt đối không commit hay gửi cho ai. Giao diện cài đặt của GitHub có thể đổi tên menu theo thời gian, hãy đối chiếu với tài liệu chính thức.

Ba vùng và vòng đời của một thay đổi

Hiểu mô hình ba vùng giúp bạn không còn bối rối với add, commit, push:

Viết commit message tốt

  • Mỗi commit làm một việc có thể mô tả gọn; dễ review, dễ hoàn tác.
  • Dòng đầu ngắn (khoảng 50–72 ký tự), dùng thể mệnh lệnh: “Fix lỗi chia cho 0 khi chuẩn hóa”.
  • Nhiều đội dùng quy ước Conventional Commits như feat:, fix:, docs:.

Thực hành: mô phỏng commit, nhánh và merge

Hãy tự gõ vài lệnh vào mô phỏng dưới đây để thấy đồ thị commit thay đổi thế nào. Thử “Kịch bản mẫu” trước, rồi tự gõ git branch, git switch, git merge.

Mô phỏng chỉ hiểu một phần nhỏ của Git: commit, branch, switch/checkout, merge, log. Nó không có file thật và không xử lý xung đột.

Hai điều đáng quan sát: (1) khi nhánh main chưa có commit mới, merge chỉ đẩy con trỏ đi tiếp (fast-forward); (2) khi hai nhánh cùng có commit mới, Git tạo merge commit có hai commit cha.

Git bên trong: đối tượng và mã băm

Git thực chất là một kho lưu trữ địa chỉ theo nội dung (content-addressable): mỗi đối tượng được lưu dưới tên là mã băm SHA-1 của nội dung. Có bốn loại đối tượng; ba loại đầu bạn gặp mỗi ngày:

LoạiChứa gìVí dụ
blobNội dung của một file (không có tên file).file config.py
treeDanh sách thư mục: chế độ file, loại, mã băm và tên.100644 blob 224cfb6… config.py
commitMã băm của tree gốc, mã băm commit cha, tác giả, người commit, thời gian, thông điệp.một “ảnh chụp” + con trỏ tới lịch sử
tagNhãn có chú thích, trỏ tới một đối tượng khác.git tag -a v1.0

Mã băm của một đối tượng là SHA-1 của chuỗi “<loại> <số byte>”, một byte 0, rồi nội dung. Bạn có thể kiểm chứng bằng tay (kết quả dưới đây là thật, chạy với Git 2.43):

$ echo 'hello' | git hash-object --stdin
ce013625030ba8dba906f756967f9e9ca394464a

$ printf 'blob 6\0hello\n' | sha1sum        # "blob 6" vì 'hello\n' dài 6 byte
ce013625030ba8dba906f756967f9e9ca394464a  -

Hai lệnh cho cùng kết quả: git hash-object không làm gì thần bí hơn việc băm đúng chuỗi đó. Giờ tạo một repo nhỏ với một commit (đặt cố định ngày giờ để kết quả tái lập):

$ git init -q -b main demo && cd demo
$ git config user.name "Ten Cua Ban"; git config user.email ban@example.com
$ echo "lr = 0.001" > config.py && git add config.py
$ GIT_AUTHOR_DATE="1700000000 +0000" GIT_COMMITTER_DATE="1700000000 +0000" git commit -q -m "Them config"

$ git cat-file -p HEAD                       # đối tượng commit
tree 2b07690e08f476a99b15e9d951b2e9267ac52730
author Ten Cua Ban <ban@example.com> 1700000000 +0000
committer Ten Cua Ban <ban@example.com> 1700000000 +0000

Them config

$ git cat-file -p 'HEAD^{tree}'              # đối tượng tree
100644 blob 224cfb60d18eb295b818b848ce5309cd62a3af5b	config.py

$ git rev-parse HEAD
472eca784fb3683d9c703b700d50e136afc1a3c4

$ cat .git/HEAD .git/refs/heads/main        # nhánh chỉ là một file 41 byte chứa mã băm
ref: refs/heads/main
472eca784fb3683d9c703b700d50e136afc1a3c4

Hai điều rút ra. (1) Một nhánh chỉ là con trỏ: tạo nhánh gần như miễn phí vì chỉ ghi thêm một file nhỏ. HEAD là file nói “tôi đang ở nhánh nào”. (2) Mã băm commit phụ thuộc vào mã băm cha: đổi bất cứ thứ gì trong một commit (nội dung, thông điệp, tác giả, giờ) sẽ đổi mã băm của nó, và vì commit sau chứa mã băm commit trước, mọi commit hậu duệ cũng đổi theo. Cấu trúc này gọi là cây Merkle; nó bảo đảm lịch sử không bị sửa lặng lẽ. Hãy thử:

Gõ nội dung file bất kỳ. Với “hello” và dấu xuống dòng ở cuối, kết quả phải đúng là ce01362… như ở trên (JavaScript trong trang tự tính SHA-1, không gọi Git). Ô cam là các bit khác nhau khi đổi ký tự đầu.

Bốn commit cùng một cây rỗng, cùng tác giả và giờ cố định, chỉ khác thông điệp (đã kiểm chứng khớp với git commit-tree thật). Đổi chữ ở commit 2 và xem các commit 2, 3, 4 đổi mã băm còn commit 1 thì không.

Từ đây dễ hiểu vì sao git rebase, git commit --amend và git reset được gọi là “viết lại lịch sử”: chúng tạo ra commit mới với mã băm mới, và vì vậy làm hỏng bản sao của những người đã kéo về commit cũ.

Kho đối tượng, nén delta và vì sao file nhị phân lớn là vấn đề

Mỗi phiên bản của một file là một blob riêng. Khi dọn dẹp (git gc) Git gói các đối tượng vào packfile và lưu các phiên bản gần giống nhau dưới dạng delta (phần khác biệt so với một bản gốc) rồi nén bằng zlib. Với text thay đổi ít, kho tăng rất chậm; với dữ liệu nhị phân có entropy cao (trọng số mô hình, ảnh nén sẵn), mỗi phiên bản gần như là một bản mới hoàn toàn. Phép đo mình chạy thật:

# (a) 5 phiên bản của một file "trọng số" ngẫu nhiên 1 MiB, mỗi lần commit một nội dung khác
for i in 1 2 3 4 5; do head -c 1048576 /dev/urandom > model.bin; git add model.bin; git commit -q -m "v$i"; done
git gc -q; git count-objects -vH | grep size-pack          # size-pack: 5.00 MiB

# (b) file text 385 KB (20 000 dòng số), sửa đúng 1 dòng ở mỗi phiên bản, 6 phiên bản
git gc -q; git count-objects -vH | grep size-pack          # size-pack: 176.23 KiB

Con số cụ thể phụ thuộc dữ liệu và phiên bản Git, nhưng xu hướng thì ổn định: (a) tăng đúng bằng 5 lần dung lượng một phiên bản, (b) 6 phiên bản chỉ tốn vài chục phần trăm của một phiên bản vì delta và nén hiệu quả. Đó là lý do trọng số mô hình nên để ở Git LFS, DVC hay kho đối tượng, còn trong Git chỉ giữ con trỏ.

Nhánh, merge, rebase và xung đột

git switch -c feature/dropout    # tạo và chuyển sang nhánh mới (Git ≥ 2.23)
# ... sửa code, commit ...
git switch main
git merge feature/dropout        # gộp nhánh vào main
git branch -d feature/dropout    # xóa nhánh đã gộp

Rebase là cách khác để tích hợp: “đặt lại” các commit của nhánh bạn lên đầu nhánh đích để lịch sử thẳng hàng.

git switch feature/dropout
git rebase main                  # chỉ làm trên nhánh của riêng bạn
Quy tắc vàng của rebaseRebase viết lại commit (tạo commit mới với mã băm mới). Đừng rebase các nhánh mà người khác đã kéo về.

Giải quyết xung đột (conflict)

Xung đột xảy ra khi hai nhánh sửa cùng vùng của cùng một file. Git đánh dấu trong file:

<<<<<<< HEAD
learning_rate = 0.001
=======
learning_rate = 0.0003
>>>>>>> feature/dropout
  1. Mở file, chọn (hoặc kết hợp) nội dung đúng, xóa ba dòng đánh dấu.
  2. git add <file> để báo đã xử lý xong.
  3. git commit (với merge) hoặc git rebase --continue (với rebase).

Nếu rối, git merge --abort hoặc git rebase --abort đưa mọi thứ về trạng thái trước khi bắt đầu.

Merge ba chiều hoạt động thế nào

Git không chỉ so hai phiên bản. Nó tìm tổ tiên chung gần nhất của hai nhánh (merge base, xem bằng git merge-base A B) rồi so mỗi nhánh với tổ tiên. Quy tắc cho từng vùng của file:

  • Chỉ một nhánh thay đổi so với tổ tiên: lấy thay đổi đó.
  • Hai nhánh thay đổi giống hệt nhau: lấy một bản.
  • Hai nhánh thay đổi khác nhau cùng vùng: xung đột, Git dừng và để bạn quyết định.

Điểm tinh tế: hai thay đổi trên hai dòng liền kề nhau (không có dòng chưa đổi ở giữa) vẫn bị coi là cùng vùng, nên cũng xung đột. Thí nghiệm thật với git merge-file (cùng thuật toán gộp ba chiều theo dòng):

$ cat base:   lr = 0.001 / epochs = 10 / batch = 32
$ ours đổi dòng 1 thành lr = 0.01; theirs đổi dòng 2 thành epochs = 20
$ git merge-file -p -L ours -L base -L theirs ours base theirs
<<<<<<< ours
lr = 0.01
epochs = 10
=======
lr = 0.001
epochs = 20
>>>>>>> theirs
batch = 32

Hãy thử trực tiếp: cài đặt thuật toán ba chiều bằng JavaScript trong trang (đã đối chiếu kết quả với git merge-file thật trên 9 tình huống, trùng khớp cả chỗ đặt dấu xung đột):

Chọn tình huống hoặc sửa ba ô văn bản. Kết quả bên dưới có dấu xung đột nếu cần. Chú ý tình huống “liền kề”: hai thay đổi không chồng lên nhau nhưng vẫn xung đột.

Để thấy cả bản gốc trong vùng xung đột (giúp quyết định đúng), bật git config --global merge.conflictStyle diff3; các phiên bản mới hơn còn có zdiff3 (hãy kiểm tra tài liệu). Thuật toán gộp mặc định gần đây của Git tên là ort (mình nhớ nó thay recursive từ Git 2.34; bạn nên kiểm tra); nó cũng xử lý đổi tên file, điều mà phép gộp theo dòng ở trên không làm.

Làm việc với remote

git clone git@github.com:<user>/<repo>.git     # tải repo về
git remote -v                                      # xem các remote
git remote add origin git@github.com:<user>/<repo>.git   # nếu bạn git init trước
git push -u origin main                            # đẩy lần đầu, nhớ upstream
git fetch origin                                   # tải thông tin mới, chưa thay đổi file của bạn
git pull                                           # fetch + tích hợp (mặc định là merge)
git pull --rebase                                  # fetch + rebase

Phân biệt fetch và pull: fetch an toàn vì chỉ cập nhật bản đồ của remote; pull còn đổi cả nhánh hiện tại của bạn.

Quy trình cộng tác trên GitHub

Quy trình “GitHub flow” gọn và phổ biến:

  1. Issue: mô tả việc cần làm hoặc lỗi cần sửa.
  2. Nhánh: tạo nhánh từ main, đặt tên có nghĩa (fix/nan-loss).
  3. Commit và push nhánh lên GitHub.
  4. Pull request: mô tả thay đổi, liên kết issue (viết Closes #12 trong mô tả để tự đóng issue khi merge).
  5. Review và CI: đồng đội nhận xét, kiểm thử tự động chạy.
  6. Merge vào main rồi xóa nhánh.

Đóng góp cho dự án của người khác (fork)

# Sau khi bấm Fork trên GitHub:
git clone git@github.com:<ban>/<repo>.git
git remote add upstream git@github.com:<chu-du-an>/<repo>.git
git fetch upstream
git switch -c fix/typo upstream/main
# sửa, commit, push lên fork của bạn rồi mở Pull Request

Chiến lược nhánh và cách gộp pull request

Khi bấm “Merge” trên một PR, GitHub thường có ba lựa chọn (tên nút có thể đổi, hãy xem tài liệu hiện hành):

Cách gộpKết quả trong mainĐánh đổi
Create a merge commitgiữ mọi commit của nhánh và thêm một merge commitlịch sử đầy đủ nhưng nhiều nhánh rẽ
Squash and mergegom cả PR thành một commit mớilịch sử gọn, mỗi PR một commit; mất commit trung gian; nhánh PR không còn là tổ tiên của main
Rebase and mergephát lại từng commit lên đầu main (mã băm mới)lịch sử thẳng, giữ từng commit; mã băm khác với trên nhánh PR

Hãy bật bảo vệ nhánh (branch protection hoặc ruleset) cho main: yêu cầu PR, yêu cầu CI xanh và ít nhất một review, chặn push thẳng và force-push. Tệp CODEOWNERS gán người review bắt buộc cho từng thư mục. Chi tiết cấu hình thay đổi theo thời gian; hãy đọc GitHub Docs.

GitHub Actions: kiểm thử tự động (CI)

Tạo file .github/workflows/ci.yml; mỗi lần push hoặc mở PR, GitHub sẽ chạy các bước bạn khai báo:

name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - run: pytest -q

Số phiên bản của các action (@v4, @v5) thay đổi theo thời gian; hãy xem trang của từng action trên GitHub Marketplace để dùng bản hiện hành. Với dự án AI, CI nên chạy kiểm thử nhỏ, nhanh (kiểm tra hình dạng tensor, hàm tiền xử lý), không huấn luyện mô hình lớn.

Giải phẫu một workflow và ma trận kiểm thử

Một workflow gồm sự kiện kích hoạt (on), một hoặc nhiều job chạy trên máy ảo riêng (song song nếu không khai báo needs), và mỗi job gồm các step chạy tuần tự trên cùng máy (uses gọi một action dựng sẵn, run chạy lệnh shell). Ví dụ gần với thực tế hơn cho một dự án Python/AI:

name: CI
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read              # quyền tối thiểu cho GITHUB_TOKEN

concurrency:                  # hủy lượt chạy cũ khi có commit mới trên cùng nhánh/PR
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        python-version: ["3.10", "3.11", "3.12"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
          cache: pip          # lưu cache gói pip giữa các lần chạy
      - run: pip install -r requirements.txt
      - run: pytest -q --maxfail=1
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: report-${{ matrix.python-version }}
          path: reports/

  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pipx run ruff check .

Hai job test và lint chạy song song; ma trận nhân test thành 3 job (mỗi phiên bản Python một job). Tổng phút chạy \(\approx\) số job \(\times\) thời lượng trung bình, ví dụ 3 job \(\times\) 4 phút \(+\) 1 job \(\times\) 1 phút \(=13\) phút máy (phút này tính vào hạn mức; hệ số tính tiền khác nhau giữa các hệ điều hành, hãy xem bảng giá hiện hành). Mẹo: cache phụ thuộc, hủy lượt chạy cũ bằng concurrency, và để huấn luyện nặng chạy theo lịch (on: schedule) hoặc thủ công (workflow_dispatch) thay vì trên mỗi commit.

Bảo mật Actions
  • Đặt permissions tối thiểu; chỉ cấp thêm quyền ghi cho job cần.
  • Đừng chèn trực tiếp dữ liệu do người ngoài kiểm soát vào lệnh shell (ví dụ run: echo ${{ github.event.pull_request.title }} có thể bị chèn lệnh). Truyền qua biến môi trường rồi dùng "$VAR".
  • Bí mật (Secrets) thường không có sẵn cho workflow chạy từ PR của fork; sự kiện pull_request_target chạy với quyền của repo đích nên cực kỳ nguy hiểm nếu checkout và chạy mã của PR: hãy đọc kỹ tài liệu trước khi dùng.
  • Action của bên thứ ba là mã chạy với quyền của bạn: ưu tiên action uy tín, cân nhắc ghim theo mã băm commit thay vì thẻ phiên bản.

GitHub Pages: xuất bản website này

Website bạn đang đọc là site tĩnh (HTML/CSS/JS), nên đưa lên GitHub Pages rất dễ:

  1. Đẩy code lên GitHub.
  2. Vào Settings → Pages của repo, chọn nguồn triển khai (từ một nhánh, hoặc GitHub Actions).
  3. Đợi workflow hoàn tất; địa chỉ dạng https://<user>.github.io/<repo>/.

Repo này đã kèm sẵn workflow .github/workflows/pages.yml. Bạn chỉ cần chọn nguồn là GitHub Actions trong Settings → Pages.

Mẫu .gitignore: đoán trước rồi kiểm chứng

Quy tắc cơ bản: *.pt khớp tên file ở mọi thư mục; dấu / ở đầu neo vào thư mục gốc; dấu / ở cuối chỉ khớp thư mục; ! đảo ngược một quy tắc phía trên. Với .gitignore gồm các dòng *.pt, !keep.pt, data/raw/, /build, .env, kết quả thật của git check-ignore trên từng đường dẫn:

Quan trọng: .gitignore chỉ áp dụng cho file chưa được theo dõi. File đã commit vẫn được theo dõi; muốn ngừng theo dõi dùng git rm --cached <file> (lịch sử cũ vẫn giữ nội dung, xem phần về bí mật). Dùng git check-ignore -v <đường-dẫn> để biết quy tắc nào đang khớp.

Lộ API key là sự cố phổ biến nhất Nếu lỡ commit khóa API hay mật khẩu, hãy thu hồi (revoke) và tạo khóa mới ngay. Xóa commit là chưa đủ vì bản cũ có thể đã được sao chép hoặc nằm trong lịch sử. Lưu bí mật trong biến môi trường hoặc file .env (đã ignore) và dùng Secrets của GitHub cho Actions. GitHub có tính năng quét bí mật (secret scanning), hãy kiểm tra tài liệu để biết phạm vi áp dụng cho tài khoản của bạn.

2. Dữ liệu và mô hình dung lượng lớn

Git không phù hợp để lưu file nhị phân lớn (dữ liệu, trọng số mô hình). GitHub từ chối file vượt một ngưỡng kích thước (khoảng 100 MB theo hiểu biết của mình, bạn nên kiểm tra giới hạn hiện hành trong tài liệu GitHub). Giải pháp thường dùng:

  • Git LFS: lưu con trỏ trong Git, nội dung thật ở kho riêng (git lfs install, git lfs track "*.bin"). Có hạn mức dung lượng và băng thông.
  • DVC (Data Version Control) hoặc lưu ở object storage / Hugging Face Hub, trong repo chỉ giữ file mô tả và script tải về.

3. Khả năng tái lập

  • Ghi rõ phiên bản thư viện (requirements.txt hoặc pyproject.toml kèm lock file).
  • Cố định seed ngẫu nhiên và lưu cấu hình mỗi lần chạy, kèm mã băm commit đã dùng.
  • Notebook: cân nhắc xóa output trước khi commit để diff gọn (có công cụ hỗ trợ như nbstripout, hãy kiểm tra tài liệu của công cụ).
  • README cần có: mục tiêu, cách cài đặt, cách chạy, kết quả chính, giấy phép.

Viết lại lịch sử: reset, rebase, cherry-pick, revert và reflog

reset: di chuyển nhánh, và chạm đến ba vùng đến đâu?

git reset <commit> di chuyển nhánh hiện tại về commit đích. Ba chế độ khác nhau ở chỗ chúng còn đụng đến staging và thư mục làm việc hay không:

Chế độCon trỏ nhánhStaging (index)Thư mục làm việc
--softdi chuyểngiữ nguyêngiữ nguyên
--mixed (mặc định)di chuyểnđặt lại theo commit đíchgiữ nguyên
--harddi chuyểnđặt lạiđặt lại (mất thay đổi chưa commit)

Kiểm chứng bằng một thí nghiệm thật: nhánh có hai commit (f.txt = a rồi b), sau đó f.txt được đổi thành c và git add, rồi lại sửa thành d (chưa add). Chạy git reset --X HEAD~1 rồi xem trạng thái:

--soft : HEAD=c1 | index(f.txt)=c | thư mục=d | git status --short: "MM f.txt"
--mixed: HEAD=c1 | index(f.txt)=a | thư mục=d | git status --short: " M f.txt"
--hard : HEAD=c1 | index(f.txt)=a | thư mục=a | git status --short: (sạch)

Nhớ rằng reset không xóa commit; chỉ là nhánh không còn trỏ tới chúng. Mọi vị trí HEAD từng đứng được ghi trong reflog (git reflog), nên “mất commit” thường cứu được bằng git reset --hard <mã-băm-cũ>. Reflog là nhật ký cục bộ, không được đẩy lên remote, và các mục cũ bị dọn sau một thời gian (mặc định vài chục ngày, hãy kiểm tra cấu hình của bạn); thay đổi chưa bao giờ được commit thì reflog không cứu được.

rebase so với merge, cherry-pick và revert

  • git cherry-pick <commit> sao chép thay đổi của một commit thành commit mới (mã băm mới) trên nhánh hiện tại. Hợp khi cần đưa riêng một bản sửa lỗi sang nhánh khác.
  • git revert <commit> tạo commit mới làm điều ngược lại; lịch sử cũ giữ nguyên nên an toàn cho nhánh đã chia sẻ (khác với reset).

Thử trực tiếp trong mô phỏng (các kịch bản mẫu đã được đối chiếu với Git thật: rebase rồi fast-forward cho lịch sử thẳng F2, F1, B, A, Initial commit; cherry-pick rồi revert cho Revert "tính năng", sửa lỗi NaN, tính năng, Initial commit):

Commit mờ là commit không còn nhánh nào trỏ tới (nhưng vẫn cứu được qua reflog). Mô phỏng không có file thật, không xử lý xung đột, và chỉ rebase được đường thẳng (không qua merge commit).

git bisect: tìm commit gây lỗi bằng tìm kiếm nhị phân

Khi một kết quả (độ chính xác, kiểm thử) đột nhiên tệ đi và bạn có \(n\) commit giữa bản tốt và bản xấu, tìm kiếm nhị phân tìm ra commit đầu tiên gây lỗi sau tối đa \(\lceil\log_2n\rceil\) lần kiểm tra thay vì \(n\). Với \(n=100\): tối đa 7 lần; \(n=1000\): 10 lần.

git bisect start HEAD HEAD~99                 # HEAD đang xấu, HEAD~99 còn tốt
git bisect run sh -c '! test -f flag.txt'     # lệnh trả 0 = tốt, khác 0 = xấu (ở đây "xấu" nếu file flag.txt tồn tại)
# → "... is the first bad commit"; thí nghiệm thật với 100 commit và lỗi bắt đầu ở commit 63 chạy 6 lần kiểm tra
git bisect reset                              # quay lại nhánh ban đầu

Với dự án AI, lệnh kiểm tra có thể là một script chạy mô hình nhỏ trên tập kiểm tra cố định và trả về mã lỗi nếu độ chính xác dưới ngưỡng. Điều kiện để bisect hoạt động: lỗi tái hiện ổn định, và mỗi commit trong khoảng đó chạy được (commit không biên dịch/không chạy được có thể đánh dấu bỏ qua bằng git bisect skip).

Bài tập

Bài 1. Tạo repo, rẽ nhánh và cố ý tạo xung đột

Tạo repo mới với file config.py chứa lr = 0.001. Trên nhánh a đổi thành 0.01, trên nhánh b đổi thành 0.0003, rồi merge cả hai vào main. Giải quyết xung đột.

Gợi ý: merge nhánh đầu sẽ fast-forward; merge nhánh thứ hai mới sinh xung đột.

Bài 2. Xuất bản trang cá nhân bằng GitHub Pages

Fork hoặc clone repo này, sửa tiêu đề trang chủ, đẩy lên GitHub và bật Pages. Mở một Pull Request vào main của repo của bạn, để CI hoặc workflow Pages chạy.

Bài 3. Dọn dẹp bí mật

Tạo repo thử, commit một file .env giả chứa API_KEY=thu-nghiem. Thêm .env vào .gitignore, dùng git rm --cached .env, commit. Sau đó trả lời: vì sao khóa vẫn còn trong lịch sử, và cần làm gì nếu đó là khóa thật?

Bài 4. Tự tính mã băm

(a) Tạo file chứa đúng hello kèm xuống dòng; chạy git hash-object và so với printf 'blob 6\0hello\n' | sha1sum. (b) Bỏ dấu xuống dòng: mã băm đổi thế nào và vì sao header đổi thành blob 5? (c) Dùng minh họa hash1 để kiểm tra.

Lời giải: (a) cả hai cho ce013625…464a. (b) printf 'hello' | git hash-object --stdin cho b6fc4c62…b5a1b0 (5 byte, header blob 5). Nội dung khác thì mã băm khác hoàn toàn.

Bài 5. Rebase hay merge?

Dùng mô phỏng git2 (hoặc repo thật) tạo: commit A trên main; nhánh feature có F1, F2; main có thêm B. (a) Gộp feature vào main bằng merge: lịch sử có bao nhiêu commit và có merge commit không? (b) Làm lại bằng rebase rồi fast-forward: lịch sử thế nào? Mã băm của F1, F2 có đổi không?

Lời giải: (a) 5 commit (Initial, A, B, F1, F2) cộng một merge commit, có hai commit cha. (b) lịch sử thẳng F2, F1, B, A, Initial commit và không có merge commit; F1, F2 được phát lại thành commit mới nên mã băm đổi (F1′, F2′).

Bài 6. Dự đoán reset

Nhánh có commit c1 (f.txt=a) và c2 (f.txt=b). Bạn sửa f.txt thành c, git add, rồi sửa tiếp thành d (không add). Với từng chế độ --soft, --mixed, --hard của git reset HEAD~1, dự đoán nội dung staging, thư mục làm việc và git status --short, rồi chạy thử để kiểm tra.

Lời giải: soft: staging = c, thư mục = d, MM; mixed: staging = a, thư mục = d, M; hard: cả hai = a, sạch. Nội dung d chỉ mất ở --hard và không cứu được bằng reflog vì chưa từng được commit.

Bài 7. bisect

Tạo 100 commit, trong đó từ commit thứ 63 trở đi có file flag.txt. Dùng git bisect run tìm commit đầu tiên có lỗi. Cần bao nhiêu lần kiểm tra? Giới hạn trên theo lý thuyết?

Lời giải: bisect báo commit 63; trong thí nghiệm của mình chạy 6 lần kiểm tra. Giới hạn trên \(\lceil\log_2100\rceil=7\).

Bài 8. Xung đột liền kề

File 3 dòng lr, epochs, batch. Nhánh A sửa dòng 1, nhánh B sửa dòng 2. Dự đoán merge có xung đột không rồi thử bằng git merge-file hoặc minh họa merge3. Nếu thêm 2 dòng không đổi vào giữa hai dòng bị sửa thì sao?

Lời giải: có xung đột, vì hai thay đổi liền kề nhau. Khi giữa hai dòng sửa có ít nhất một dòng không đổi (trường hợp “xa nhau” trong minh họa) thì gộp sạch.

Bài 9. Viết .gitignore

Viết .gitignore bỏ qua mọi checkpoint *.ckpt trừ best.ckpt, thư mục wandb/ ở mọi cấp, nhưng chỉ /outputs ở gốc. Kiểm tra bằng git check-ignore -v.

Lời giải: *.ckpt, !best.ckpt, wandb/, /outputs. Chú ý !best.ckpt phải nằm sau *.ckpt; và nếu một thư mục cha đã bị bỏ qua thì không thể “bỏ bỏ qua” file bên trong nó.
